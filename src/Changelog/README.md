# Changelog

В это разделе (левое меню) автоматически публикуются ссылки на новые сборки enterprise-версии. Актуальной считать версию от ближайщей даты. Если таких несколько - то с более высоким индексом.

Можно обновляться на несколько версий сразу, если не указано иного. Ниже на странице — [лента релизов](#лента-релизов) со всеми версиями; сначала прочитайте предупреждения об обновлении.


::: danger ⚠️ С версии 6.6.XXXX требуется лицензия v2 для каждой Enterprise-инсталляции
`6.6.XXXX` — блокирующий выпуск placeholder: перед публикацией релиза его необходимо заменить
на фактический номер версии. Пока номер не подтверждён, не подставляйте предполагаемую версию.

Начиная с версии **6.6.XXXX** каждая Enterprise-инсталляция должна использовать заново
выпущенный ключ **`LICENSE_KEY_V2`**. Переменная **`LICENSE_KEY`**, лицензии v1 и ранее выданные
ключи этой версией больше не принимаются.

**Получите полный код активации до обновления или во время согласованного окна обновления:**

1. Составьте список всех инсталляций: production, тестовых контуров, резервных площадок (DR)
   и клонов.
2. На каждой работающей инсталляции откройте **`/admin-onboarding`** (например,
   `https://ваш-домен/admin-onboarding`) и скопируйте **весь код активации без сокращения**.
3. Передайте полный код менеджеру и получите отдельный `LICENSE_KEY_V2` для этой инсталляции.
4. Добавьте `LICENSE_KEY_V2` в конфигурацию или хранилище секретов. Значение `LICENSE_KEY`
   сохраните в защищённом хранилище до окончания согласованного окна отката.
5. Обновите приложение, перезапустите все его экземпляры, дождитесь успешных health checks
   и проверьте статус лицензии и доступ лицензированного обычного пользователя.

Один ключ нельзя переносить между инсталляциями. Отдельный ключ нужен для production,
каждого тестового контура, DR-площадки и каждого клона.

**Если система уже обновлена без `LICENSE_KEY_V2`:** бэкенд может запуститься в заблокированном
лицензионном режиме, чтобы владелец — учётная запись из администраторской команды — мог пройти
восстановление. Откройте `/admin-onboarding`, скопируйте полный код активации, получите ключ у
менеджера, задайте `LICENSE_KEY_V2` и перезапустите все экземпляры приложения. Данные при этом
не теряются. Сам по себе запуск бэкенда или успешный health check не означает, что обычным
пользователям доступна лицензированная работа.

Подробнее — в разделе [«Активация инсталляции»](/operation/License.md#активация-инсталляции).
:::

::: danger ⚠️ С версии 6.6.5952 требуется расширение PostgreSQL `pgvector`
Начиная с версии [6.6.5952](./6.6.5952.md) (от 09.06.2026) расширение **pgvector** — **обязательное требование платформы**: на нём работает **быстрый универсальный (семантический) поиск** по вашим данным — это нужно **всем установкам, независимо от наличия AI-модуля**. База знаний AI-чата — лишь один из потребителей этого движка, а не причина требования.

Без расширения миграция базы не выполнится и бэкенд **не запустится** (мягкой деградации нет). Версии **до `6.6.5694` включительно** расширение не требовали — при обновлении с них подготовьте PostgreSQL **до** смены версии приложения:

1. Переведите PostgreSQL на сборку с pgvector — например, образ **`pgvector/pgvector:pgXX`** под вашу мажорную версию PostgreSQL (`pg15`/`pg16`/`pg17`); для enterprise доступно внутреннее зеркало `cr.selcloud.ru/stormbpmn-enterprise/pgvector:pg17`. Либо установите пакет расширения в текущую СУБД (например, `postgresql-17-pgvector`) и перезапустите её. Для управляемых БД (DBaaS) убедитесь, что провайдер предоставляет `pgvector`.
2. Заранее заведите расширения в **базе приложения** (от суперпользователя или роли с правом `CREATE EXTENSION`):

```sql
CREATE EXTENSION IF NOT EXISTS vector;     -- pgvector, обязательно с 6.6.5952
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS hstore;
CREATE EXTENSION IF NOT EXISTS pg_trgm;     -- автодополнение пользователей (приложение не создаёт его само)
```

Подробности и порядок обновления — в [описании версии 6.6.5952](./6.6.5952.md). Полный список расширений, кодировку БД и рекомендации по образу см. в разделе [«Требования к PostgreSQL»](/install/README.md). Про саму базу знаний — [«База знаний AI-чата»](/ai/KnowledgeBase.md).
:::

::: warning Миграция на Spring Boot 3 (версия 6.6.3748+)
С версии 6.6.3748 выполнен переход на Spring Boot 3 и Java 21. Перед обновлением проверьте:
- **PATH**: Должен указывать на `/opt/java/openjdk/bin` вместо `/usr/local/openjdk-11/bin`
- **JWTSECRET**: Минимум 64 символа (ключ HS512, 512 бит) — с коротким ключом вход упадёт с `WeakKeyException`

Подробнее см. [Версия 6.6.3748](./6.6.3748.md#%EF%B8%8F-%D0%B8%D0%B7%D0%BC%D0%B5%D0%BD%D0%B5%D0%BD%D0%B8%D1%8F-%D0%B4%D0%BB%D1%8F-enterprise-%D0%BA%D0%BB%D0%B8%D0%B5%D0%BD%D1%82%D0%BE%D0%B2)

::: warning Ограничение на размер административной команды (версия 6.6.4630+)
С версии 6.6.4630 введено ограничение на количество учётных записей в административной команде (флаг `full_access` в БД).

**Почему:** все участники такой команды обладали всеми полномочиями в системе вне зависимости от настроек прав. Чтобы избежать ошибок, мы:
- разрешили иметь **максимум 2 учётные записи** в административной команде;
- запретили добавлять новых участников в неё.

**Что делать, если в административной команде уже больше 2 участников:**
1. Создайте новую команду через админку.
2. Добавьте в неё новую учётную запись или перенесите туда учётку администратора.
3. В БД у **текущей** административной команды снимите флаг `full_access`.
4. В БД у **новой** команды поставьте флаг `full_access`.

Это может потребовать дополнительной лицензии, но мы всегда выдаём +1 место именно для этих целей.
:::
