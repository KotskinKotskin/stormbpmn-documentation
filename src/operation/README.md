# Администрирование системы

> 🔧 **Система уже работает и её надо поддерживать?** Мониторинг, резервные копии, обновление версии и восстановление после сбоев — всё здесь.

Руководство по мониторингу, резервному копированию, обновлению и устранению неисправностей StormBPMN Enterprise.

::: tip Основные задачи администратора

-   **Мониторинг** - отслеживание состояния системы и производительности
-   **Резервное копирование** - регулярное сохранение данных
-   **Обновления** - установка новых версий и исправлений
-   **Устранение неисправностей** - диагностика и решение проблем

:::

## Мониторинг системы

### Метрики Prometheus

StormBPMN предоставляет HTTP-endpoint с метриками в формате Micrometer для мониторинга через Prometheus.

**Конфигурация Prometheus:**

```yaml
- job_name: "stormbpmn-node-1"
  metrics_path: "/actuator/prometheus"
  scrape_interval: 15s
  static_configs:
      - targets: ["10.1.0.3:8080"]
```

::: tip Готовый дашборд Grafana
Используйте [Spring Boot Statistics Dashboard](https://grafana.com/grafana/dashboards/12835-spring-boot-statistics-6756-tomcat/) для визуализации метрик.
:::

### Настройка алертов

Рекомендуемые пороги для срабатывания алертов:

| Метрика                    | Условие срабатывания    | Описание                    |
| -------------------------- | ----------------------- | --------------------------- |
| **CPU Usage**              | > 90% в течение 5 минут | Высокая загрузка процессора |
| **Request Count /api/v1/** | > 100 запросов в минуту | Аномально высокая нагрузка  |
| **HEAP Memory Used**       | > 90% в течение 5 минут | Нехватка памяти JVM         |
| **No Data**                | > 5 минут без данных    | Недоступность сервиса       |

::: warning При срабатывании алертов
Переходите к разделу [Disaster Recovery](#при-базовои-эксплуатации)
:::

### Health Checks

StormBPMN предоставляет эндпоинты для проверки состояния:

```yaml
livenessProbe:
    httpGet:
        path: /api/health/liveness
        port: 8080
    initialDelaySeconds: 30
    periodSeconds: 5

readinessProbe:
    httpGet:
        path: /api/health/readiness
        port: 8080
    initialDelaySeconds: 30
    periodSeconds: 5
```

## Резервное копирование

### Что необходимо копировать

Диаграммы, описания и пользователи хранятся в PostgreSQL. Лицензионные секреты
`LICENSE_KEY_V2` и временно используемый или сохранённый для отката `LICENSE_KEY` находятся
вне базы данных: включите их защищённое хранилище в DR-процедуру или предусмотрите отдельное
восстановление секретов.

::: tip База данных, файлы и секреты
PostgreSQL содержит основные данные. S3-файлы (изображения, документы) также рекомендуется
включить в backup-стратегию, а внешние секреты, включая актуальные лицензионные ключи,
необходимо сохранять в защищённом хранилище.
:::

### Создание резервной копии

**Пример команды для PostgreSQL:**

```bash
pg_dump -h localhost -d storm_db -U storm_user -W -Ft -b > /backup/storm_$(date +%Y%m%d_%H%M%S).tar
```

**Рекомендуемый скрипт автоматизации:**

```bash
#!/bin/bash
BACKUP_DIR="/backup/stormbpmn"
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="$BACKUP_DIR/storm_backup_$DATE.tar"

# Создание резервной копии
pg_dump -h $DB_HOST -d $DB_NAME -U $DB_USER -W -Ft -b > $BACKUP_FILE

# Проверка успешности
if [ $? -eq 0 ]; then
    echo "Backup successful: $BACKUP_FILE"
    # Отправка уведомления об успехе
else
    echo "Backup failed!"
    # Отправка алерта администратору
fi

# Очистка старых копий (старше 30 дней)
find $BACKUP_DIR -name "storm_backup_*.tar" -mtime +30 -delete
```

### Требования к резервному копированию

-   [ ] **Ежедневное расписание** - автоматическое создание копий
-   [ ] **Мониторинг места** - контроль свободного пространства
-   [ ] **Уведомления** - информирование о статусе backup
-   [ ] **Тестирование** - регулярная проверка восстановления
-   [ ] **Удаленное хранение** - копии в другом дата-центре

## Восстановление из резервной копии

### Восстановление PostgreSQL

```bash
# Остановка приложения
docker stop stormbpmn

# Восстановление базы данных
pg_restore --format=t -c -N -O -h localhost -p 5432 -U storm_user -d storm_db /backup/storm_backup_20231201_120000.tar

# Запуск приложения
docker start stormbpmn
```

### Проверка восстановления

1. **Проверьте подключение** к базе данных
2. **Убедитесь в работе** health checks
3. **Восстановите лицензионные секреты** из защищённого хранилища: `LICENSE_KEY_V2` и, пока
   инсталляция использует v1 или допускает откат на него, `LICENSE_KEY`
4. **Проверьте выбранный режим лицензии**: для v1 подтвердите работу с восстановленным
   `LICENSE_KEY`; для v2 сравните полный код активации на `/admin-onboarding` с кодом, для
   которого выдан ключ, и при изменении получите перевыпущенный ключ для этой инсталляции
5. **Проверьте лицензию обычным пользователем**: выполните вход и откройте лицензированную функцию
6. **Протестируйте основные функции** (например, создание диаграммы)
7. **Проверьте логи** на наличие ошибок

## Обновление версии

### Процедура обновления

| Шаг | Действие                                      | Описание                                     |
|-----|-----------------------------------------------|----------------------------------------------|
| 0   | **Сделать бэкап базы данных**                 |                                              |
| 1   | **Убедиться, что бэкап базы разворачивается** |                                              |
| 2   | **Определить текущую версию**                 | `docker images \| grep stormbpmn`            |
| 3   | **Изучить changelog**                         | [Журнал изменений](/Changelog/README.md)     |
| 4   | **Выбрать целевую версию**                    | Проверить совместимость                      |
| 4.1 | **Инвентаризировать все инсталляции**        | Production, тестовые контуры, DR и клоны. На каждой снять код активации с `/admin-onboarding` и заранее запросить `LICENSE_KEY_V2` — см. [где взять код](/operation/License.md#где-взять-код-активации-на-существующеи-инсталляции) |
| 4.2 | **Спланировать миграцию лицензий**           | Существующий `LICENSE_KEY` работает временно; v2 можно внедрять по инсталляциям |
| 5   | **Создать резервную копию**                   | Обязательно перед любым обновлением          |
| 6   | **Сохранить текущий образ**                   | `docker save stormbpmn:current > backup.tar` |
| 7   | **Скачать новую версию**                      | `docker pull stormbpmn....`                  |
| 8   | **Подготовить миграцию на v2**               | Сначала обновить образ с рабочим `LICENSE_KEY`; затем подставить полученный заранее `LICENSE_KEY_V2` по [порядку активации](/operation/License.md#активация-инсталляции) |
| 9   | **Обновить тег в текущем контейнере**         | Изменить версию образа                       |
| 10  | **Перезапустить все экземпляры приложения**   | `docker-compose up -d`                       |
| 11  | **Проверить health checks и лицензию**        | Проверить текущий режим и доступ обычного пользователя. При миграции на v2 проверить AI/DES и удалять `LICENSE_KEY` только после успешной проверки и окончания окна отката |

### Обновление без простоя

Миграции базы данных выполняет само приложение при старте (Liquibase). Если одновременно
стартуют несколько экземпляров, миграции применяет один из них, остальные ждут блокировку в
таблице `databasechangeloglock` и стартуют после него.

| Схема установки | Что происходит при обновлении |
| --- | --- |
| Один экземпляр (Docker, Podman, одна реплика в Kubernetes) | Короткий перерыв: старый контейнер останавливается, новый применяет миграции и стартует. Обычно до 15 минут: первый старт с миграциями занимает до 5 минут |
| Две и более реплики в Kubernetes | Без простоя. Чарт обновляет поды по одному (`maxSurge: 1`, `maxUnavailable: 0`): новый под применяет миграции, проходит readiness-проверку и только после этого старый под выводится из балансировки |

Миграции пишутся так, чтобы предыдущая версия приложения продолжала работать на обновлённой
схеме: новые колонки и таблицы добавляются, существующие не удаляются и не переименовываются в
том же релизе. Так же, перекатом по узлам, обновляется наш облачный сервис. Обновления, которые требуют
особых действий, перечислены в разделе «Критические обновления» ниже — прочитайте его перед
обновлением.

Во время переката открытые соединения со старым подом (совместное редактирование, AI-чат)
обрываются, поэтому обновление лучше планировать на нерабочее время.

::: tip Пропустили несколько версий
Обновляться можно сразу через несколько версий: миграции всех промежуточных версий применятся
по порядку при старте. Перед этим прочитайте «Критические обновления» для каждой пропущенной
версии.
:::

### Откат версии

Обратных миграций нет: откатить схему базы средствами приложения нельзя. Есть два способа
отката.

| Способ | Когда подходит | Как |
| --- | --- | --- |
| Только образ | Новая версия запустилась, но в ней ошибка в работе, данные в порядке | Верните предыдущий тег образа (`helm rollback <релиз> -n <namespace>` или прежний тег в `docker-compose.yml`) и перезапустите. Предыдущая версия работает на обновлённой схеме: миграции новой версии только добавляют структуры. Записи новых миграций в `databasechangelog` старой версии не мешают |
| Образ и база | Миграция завершилась ошибкой, данные повреждены или в Changelog релиза указано, что откат образа невозможен | Остановите все экземпляры, восстановите базу из резервной копии, сделанной перед обновлением, и запустите предыдущий образ — см. [«Disaster Recovery → При обновлении»](#при-обновлении). Изменения, внесённые пользователями после обновления, при этом теряются |

Поэтому перед каждым обновлением обязательны резервная копия базы и проверка, что она
разворачивается (шаги 0–1 выше).

::: tip Лента «Что нового»
В on-prem версии лента «Что нового» отображает статичный контент, запечённый в образ при сборке. Внешние ссылки на блог отсутствуют, дата отображается как дата сборки. Обновление ленты происходит автоматически при обновлении версии приложения.
:::

### Критические обновления

::: danger Версия ≥ 7.10.13 — переходный режим лицензирования v1/v2
Существующий `LICENSE_KEY` временно продолжает работать, поэтому немедленный перевыпуск всех
ключей не требуется. V1 устарел и имеет известное ограничение безопасности: мигрируйте
production, тестовые контуры, DR и клоны постепенно, получая для каждого отдельный
`LICENSE_KEY_V2`. Непустой v2 имеет исключительный приоритет, и при его ошибке автоматического
возврата к v1 нет. После подстановки v2 перезапустите все экземпляры, проверьте лицензию и
только затем удалите `LICENSE_KEY` из рабочей конфигурации этой инсталляции. Подробности —
[«Активация инсталляции»](/operation/License.md#активация-инсталляции).
:::

::: danger Версия < 6.3.231 → новее
**Требуется миграция базы данных:**

```sql
UPDATE databasechangelog
SET filename = CONCAT('/db/changelog/changes/', SUBSTRING(filename, 35));
```

:::

::: warning Версия ≥ 6.6.441
**Требуются новые ENV переменные:**

| Переменная                     | Значение                | Описание                             |
| ------------------------------ | ----------------------- | ------------------------------------ |
| **STORM_ALLOWED_ORIGINS**      | `https://your.domain`   | CORS настройки (не используйте `*`!) |
| **STORM_DISABLE_SIMPLE_AUTH**  | `false`                 | Отключение базовой авторизации       |
| **STORM_DISABLE_ENV_IN_UI**    | `true`                  | Скрытие ENV в админке                |
| **STORM_DISABLE_ANON_SHARING** | `true`                  | Запрет анонимного доступа            |
| **STORM_SENTRY_ENABLE**        | `false`                 | Отключение Sentry                    |
| **STORM_ENABLE_SAAS_FEATURES** | `false`                 | Отключение SaaS функций              |
| **GOTENBERG_URL**              | `http://gotenberg:3001` | URL сервиса конвертации              |

:::

::: warning Версия ≥ 6.6.559
**Требуется расширение PostgreSQL:**

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

:::

::: danger Расширение pgvector станет обязательным (быстрый поиск + база знаний)
Расширение **pgvector** становится **базовым требованием платформы**: на нём работает быстрый универсальный (семантический) поиск по данным — это нужно **всем установкам, независимо от наличия AI-модуля** (база знаний AI-чата — лишь один из потребителей). В ближайших версиях pgvector станет **жёсткой зависимостью**: без него миграция не выполнится и бэкенд не запустится. **Готовьтесь заранее** (можно уже сейчас):

1. Перейдите на сборку PostgreSQL с pgvector — например, образ **`pgvector/pgvector:pg17`** (тот же PostgreSQL + стандартные contrib-модули + pgvector), либо установите pgvector в свою сборку/DBaaS.
2. Убедитесь, что в **базе приложения** доступны нужные расширения. Достаточно прав суперпользователя или роли с правом `CREATE EXTENSION`:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS hstore;
CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- для автодополнения, приложение его не создаёт само
```

Полный список расширений и кодировка БД — в разделе [«Требования к PostgreSQL»](/install/README.md).
:::

## Disaster Recovery

### При обновлении

Если обновление прошло неудачно:

1. **Сохранить логи контейнера**

    ```bash
    docker logs stormbpmn > /tmp/update_error_logs.txt
    ```

2. **Восстановить базу данных**

    ```bash
    pg_restore --format=t -c -N -O -h localhost -p 5432 -U storm_user -d storm_db /backup/latest_backup.tar
    ```

3. **Откатить версию контейнера**

    ```bash
    docker load < backup_image.tar
    docker-compose up -d
    ```

    Для отката лицензии сохраните обе переменные до конца согласованного окна. Непустой
    `LICENSE_KEY_V2` имеет приоритет; чтобы временно вернуться к v1, удалите или очистите v2,
    восстановите `LICENSE_KEY` и перезапустите все экземпляры приложения.

4. **Перезапустить контейнеры**

    ```bash
    docker-compose restart
    ```

5. **Проверить восстановление**: дождитесь health checks, проверьте статус лицензии, затем
   выполните вход и откройте лицензированную функцию под обычной учётной записью.

6. **Обратиться в поддержку** с информацией:
    - Исходная версия
    - Целевая версия
    - Логи ошибок
    - Конфигурация системы

### При базовой эксплуатации

При проблемах в работе системы:

1. **Сохранить логи**

    ```bash
    docker logs stormbpmn > /tmp/error_logs.txt
    ```

2. **Перезапустить контейнеры**

    ```bash
    docker-compose restart
    ```

3. **Проверить состояние**

    - Health checks отвечают
    - Метрики в норме
    - Пользователи могут войти

4. **При сохранении проблем** - обращение в поддержку
